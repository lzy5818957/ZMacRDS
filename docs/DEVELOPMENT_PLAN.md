## 第一个决策

先证明两个已经登录的 macOS 账号可以同时产生不同的实时画面，并分别接收键盘和鼠标输入。若操作系统只向前台账号提供画面或只能在前台投递输入，再好的 RDP 编码器也无法提供独立桌面。此实验先在目标 Apple Silicon Mac 的具体 macOS 构建上进行。使用两个普通测试账号、两份合成测试数据，记录 macOS 与 Windows 的版本及显示配置。

第一个可用版本同时面向 Windows 11 自带的 `mstsc.exe` 和 macOS 上的 Microsoft Windows App。服务端运行在 Mac 上，两种客户端通过同一 RDP 入口使用各自账号登录。必须支持 Windows / Windows、Mac / Mac、Windows / Mac 三种组合，用户同时工作时各有独立桌面；断线后可从任一受支持客户端回到自己的原有应用。客户端选择、兼容范围与记录格式见[客户端兼容与并发验收](CLIENT_TEST.md)。第一版允许管理员提前登录实验账号。冷启动后远程创建新的 Aqua 图形会话是另一项单独验收的能力。

## 分阶段交付

| 阶段 | 开发内容 | 验收与停止条件 |
| --- | --- | --- |
| M0 · 确认会话身份 | 按[双账号操作单](M0_TEST.md)在两个账号中启动临时 LaunchAgent，轮换前台并核对两份采样日志。 | 两个代理的 UID 和审计会话可区分，GUI UID 均与各自账号相符。单次命令行诊断不算通过双账号实验。 |
| M1 · 本地双桌面实验 | 每个代理通过 ScreenCaptureKit 采集本账号的测试窗口，然后测试整桌面。先做只读预览，再把测试键鼠事件送入该代理所在会话。使用单独的测试窗口记录收到的事件和焦点。 | 通过下方 A/B 测试。后台桌面黑屏、停止刷新或任一输入落到其他账号即失败。失败时保存复现条件，暂停 RDP 集成。 |
| M2 · Mac 与 Windows 客户端连接 | 单独用 IronRDP 服务端样例分别跑通 `mstsc.exe`、macOS Windows App 和动态测试图，再接入一个已验证的代理。第一版采用位图更新，按连接协商能力，处理分辨率、缩放、两端修饰键、按键释放和鼠标坐标。 | 两种客户端分别通过受信任测试证书建立加密连接，显示实时画面，完成点击、拖动、中英文输入与断线重连。记录各自实际协商到的安全模式和输入映射；两端均通过才完成 M2。 |
| M3 · 同平台与混合双用户并发 | 单一 RDP 入口进行身份验证；由会话管理服务把已认证身份绑定到本地 UID，再连接该用户的代理。加入跨客户端重连、同账号新连接接管旧连接、注销和代理崩溃处理。 | Windows / Windows、Mac / Mac、Windows / Mac 三种组合各并行操作两个 macOS 桌面 30 分钟，完成下方隔离测试及 CLIENT_TEST 中的恢复测试，再各自在 Codex 的独立工作目录中完成一个可辨认的小任务。 |
| M4 · 扩展到 32 人 | 在目标 Mac Pro 上依次跑 2、4、8、16、32 个独立图形用户，每档包含 Mac / Windows 混合连接，记录客户端比例、硬件、系统版本、分辨率、负载和性能。容量瓶颈出现后再决定是否引入硬件视频编码。 | 每一级先通过隔离与恢复测试，再进行性能测量。32 人目标为两种客户端合计 32 个独立用户；只发布实测通过的人数、客户端组合、配置和负载。 |

## 双用户实验操作单

1. 在两个账号 A、B 内分别打开测试窗口，显示不同颜色、随机标记和每秒变化的计数器。保留本地观察记录，避免提交真人桌面截图。将 A 切至后台，保持 B 在前台，再反向重复。两个代理均要持续捕获对应账号的新帧。
2. 两侧同时输入各自的随机文本、点击不同位置并拖动，各重复 100 次。分别对照两个接收窗口的记录。要求无错投、无跨账号焦点变化，远程操作后台账号时不得切换本机前台账号。需同时验证整桌面与跨应用交互；只向指定测试进程定向投递事件不足以证明桌面可用。
3. 在单屏、有外接屏或无头模式分别记录结果。添加虚拟显示器后重做隔离测试，确认它属于预期会话。仅增加显示器数量不能作为新增用户会话的证据。
4. 断开 A 并重连，原窗口和文档仍在，B 的画面与输入不受影响。注销 A 或撤销 A 的录屏权限后，应关闭或拒绝 A 的流，不得回落到 B 或控制台桌面。退出 A 后重新登录，要将其视作新会话，拒绝复用旧代理注册。
5. 记录权限、样本时长、帧更新时间、错投计数和复现步骤。Codex 测试使用两个独立账号、两份无敏感信息的工作目录；验收人的操作和 Codex Computer Use 自动操作分别记录。

## 组件与边界

| 组件 | 建议实现 | 职责 |
| --- | --- | --- |
| macOS 用户代理 | Swift 或 Objective-C，运行在各自已登录的 Aqua 会话 | 在本用户的授权范围内采集画面、处理输入和桌面变化。ScreenCaptureKit 及系统输入接口对非前台会话的行为必须由 M1 实测。 |
| 会话管理 | 本机独立服务，本地 IPC | 把已认证身份映射到允许的本机 UID；校验 IPC 对端的系统身份及会话，用会话代次区分注销与重新登录。未登录、已锁定或无法验证时返回明确错误。 |
| RDP 入口 | Rust + IronRDP 作为首选候选 | 对 `mstsc.exe` 和 macOS Windows App 提供同一入口，负责协议协商、认证、图像更新、输入和断开恢复。分辨率、编码、键盘和连接状态按连接维护，身份与桌面归属由会话管理决定。先用动态测试图排除协议问题；在可行性实验中只监听回环地址，可从实验网络通过隧道访问。 |

同一身份再次通过认证后，新客户端接管原桌面，旧客户端断开，无论两个客户端的平台是否相同；错误凭据不得踢掉已有连接。网络异常后的控制权释放、旧连接失效和新连接绑定必须原子化，避免两个客户端同时向同一会话发送输入。恢复时重新协商客户端能力，保留服务端桌面与应用；不能用客户端系统、分辨率或设备名称决定桌面归属。未认证或身份不匹配的连接一律不得接收画面或投递输入。数字 UID、端口号或客户端提交的用户名都不能单独充当身份凭证。剪贴板、磁盘映射和麦克风保持关闭。RDP 应用声音已加入按 UID 的私有进程筛选，只有客户端协商输出音频后启用；当前验收范围见[声音与常驻服务报告](reports/AUDIO_SERVICE_2026-11-05.md)，实际 Windows 客户端仍待测试。

## 容量测试与决策

每档固定分辨率和目标帧率，分别测空闲桌面、持续打字和滚动、多人同时运行 Codex 三种负载。Mac 与 Windows 客户端各占一半，32 人档即 16 + 16；客户端不足时记录实际比例和未测项，不标为该档完整通过。每档运行 30 分钟，记录每会话内存、整机内存压力与交换、CPU/GPU、网络吞吐、有效帧率、输入到画面更新的 p95 延迟及断线次数，按客户端平台分别汇总交互指标。首轮局域网交互目标为 1080p、滚动时至少 15 fps、p95 小于 200 ms；这些数字是验收目标。通过 32 人档后做 8 小时稳定性测试，并在有负载时模拟一名用户退出和一名用户跨平台重连。

如果 M1 仅能采集当前控制台，先保留可复现的最小样例，分别排查采集权限、窗口归属和非前台会话的输入投递。不能证明完整隔离时，项目状态停在已验证的单用户能力。若 M3 可用但容量不足，以实测稳定并发为准，并区分主机瓶颈与 Codex 服务端限额。
