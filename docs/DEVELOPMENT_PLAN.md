# ZMacRDS 开发计划

## 第一个决策

先证明两个已经登录的 macOS 账号可以同时产生不同的实时画面，并分别接收键盘和鼠标输入。若操作系统只向前台账号提供画面或只能在前台投递输入，再好的 RDP 编码器也无法提供独立桌面。此实验先在目标 Apple Silicon Mac 的具体 macOS 构建上进行。使用两个普通测试账号、两份合成测试数据，记录 macOS 与 Windows 的版本及显示配置。

第一个可用版本的入口是 Windows 11 自带的 `mstsc.exe`。两个用户要能同时工作，断线后回到各自原来的应用。第一版允许管理员提前登录实验账号。冷启动后远程创建新的 Aqua 图形会话是另一项单独验收的能力。

## 分阶段交付

| 阶段 | 开发内容 | 验收与停止条件 |
| --- | --- | --- |
| M0 · 确认会话身份 | 在各账号的 Terminal 运行仓库中的 `session-probe`。下一步用每用户 LaunchAgent 重复取样，记录进程 UID、GUI UID、审计会话、前后台状态及所需权限。 | 两个代理的 UID 和审计会话可区分，GUI UID 均与各自账号相符。单次命令行诊断不算通过双账号实验。 |
| M1 · 本地双桌面实验 | 每个代理通过 ScreenCaptureKit 采集本账号的测试窗口，然后测试整桌面。先做只读预览，再把测试键鼠事件送入该代理所在会话。使用单独的测试窗口记录收到的事件和焦点。 | 通过下方 A/B 测试。后台桌面黑屏、停止刷新或任一输入落到其他账号即失败。失败时保存复现条件，暂停 RDP 集成。 |
| M2 · 首次 Windows 连接 | 单独用 IronRDP 服务端样例跑通 `mstsc.exe` 和动态测试图，再接入一个已验证的代理。第一版采用位图更新，处理分辨率、修饰键、按键释放和鼠标坐标。 | Windows 能通过受信任测试证书建立加密连接，显示实时画面，完成点击、拖动、中英文输入与断线重连。记录实际协商到的安全模式。 |
| M3 · 两名 Windows 用户同时工作 | 单一 RDP 入口进行身份验证；由会话管理服务把已认证身份绑定到本地 UID，再连接该用户的代理。加入重连、注销和代理崩溃处理。 | 两个独立的 Windows 客户端并行操作两个 macOS 桌面 30 分钟，完成下方隔离测试，再各自在 Codex 的独立工作目录中完成一个可辨认的小任务。 |
| M4 · 扩展到 32 人 | 在目标 Mac Pro 上依次跑 2、4、8、16、32 个独立图形用户，记录硬件、系统版本、分辨率、负载和性能。容量瓶颈出现后再决定是否引入硬件视频编码。 | 每一级先通过隔离与恢复测试，再进行性能测量。只发布实测通过的人数、配置和负载。 |

## 双用户实验操作单

1. 在两个账号 A、B 内分别打开测试窗口，显示不同颜色、随机标记和每秒变化的计数器。保留本地观察记录，避免提交真人桌面截图。将 A 切至后台，保持 B 在前台，再反向重复。两个代理均要持续捕获对应账号的新帧。
2. 两侧同时输入各自的随机文本、点击不同位置并拖动，各重复 100 次。分别对照两个接收窗口的记录。要求无错投、无跨账号焦点变化，远程操作后台账号时不得切换本机前台账号。需同时验证整桌面与跨应用交互；只向指定测试进程定向投递事件不足以证明桌面可用。
3. 在单屏、有外接屏或无头模式分别记录结果。添加虚拟显示器后重做隔离测试，确认它属于预期会话。仅增加显示器数量不能作为新增用户会话的证据。
4. 断开 A 并重连，原窗口和文档仍在，B 的画面与输入不受影响。注销 A 或撤销 A 的录屏权限后，应关闭或拒绝 A 的流，不得回落到 B 或控制台桌面。退出 A 后重新登录，要将其视作新会话，拒绝复用旧代理注册。
5. 记录权限、样本时长、帧更新时间、错投计数和复现步骤。Codex 测试使用两个独立账号、两份无敏感信息的工作目录；验收人的操作和 Codex Computer Use 自动操作分别记录。

## 组件与边界

| 组件 | 建议实现 | 职责 |
| --- | --- | --- |
| macOS 用户代理 | Swift 或 Objective-C，运行在各自已登录的 Aqua 会话 | 在本用户的授权范围内采集画面、处理输入和桌面变化。ScreenCaptureKit 及系统输入接口对非前台会话的行为必须由 M1 实测。 |
| 会话管理 | 本机独立服务，本地 IPC | 把已认证身份映射到允许的本机 UID；校验 IPC 对端的系统身份及会话，用会话代次区分注销与重新登录。未登录、已锁定或无法验证时返回明确错误。 |
| RDP 入口 | Rust + IronRDP 作为首选候选 | 负责协议协商、认证、图像更新、输入和断开恢复。先用动态测试图排除协议问题；在可行性实验中只监听回环地址，可从实验网络通过隧道访问。 |

同一用户名的重复连接，第一版拒绝第二个控制端；原控制端断开后允许同一身份恢复。未认证或身份不匹配的连接一律不得接收画面或投递输入。数字 UID、端口号或客户端提交的用户名都不能单独充当身份凭证。默认关闭剪贴板、磁盘映射和音频；后续只在验证按用户隔离后开启。

## 容量测试与决策

每档固定分辨率和目标帧率，分别测空闲桌面、持续打字和滚动、多人同时运行 Codex 三种负载。每档运行 30 分钟，记录每会话内存、整机内存压力与交换、CPU/GPU、网络吞吐、有效帧率、输入到画面更新的 p95 延迟及断线次数。首轮局域网交互目标为 1080p、滚动时至少 15 fps、p95 小于 200 ms；这些数字是验收目标。通过 32 人档后做 8 小时稳定性测试，并在有负载时模拟一名用户退出和一名用户重连。

如果 M1 仅能采集当前控制台，先保留可复现的最小样例，分别排查采集权限、窗口归属和非前台会话的输入投递。不能证明完整隔离时，项目状态停在已验证的单用户能力。若 M3 可用但容量不足，以实测稳定并发为准，并区分主机瓶颈与 Codex 服务端限额。
