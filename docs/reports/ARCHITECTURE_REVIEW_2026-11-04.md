# 远程桌面链路审查与改造决策

后续实施与受限模式回归已更新至 [2026-11-05 记录](REFACTOR_VM03_2026-11-05.md)。下文保留 11 月 4 日审查时的证据、判断和待办，不代表后续改动尚未落地。

本轮目标：用成熟开源实现审查整个系统，替代按可见症状逐项修补。当前结论是 **VNC 优先，RDP 保留为待验收的实验后端**。RDP 黑块仍可复现，未修复；当前也没有达到流畅度验收的证据。

## 一、证据与边界

VM03 为 4 核、8 GB、1920×1200，运行三个独立 GUI 账号。三种连接的输入归属已核对，不能据此推断客户端渲染性能通过。

使用同一 `tools/m3-motion.m` 的 30 Hz 移动窗口负载，分别在 rdp 和 vnc 账号运行，使用 `nettop -P -L 5 -s 1 -J bytes_in,bytes_out` 记录对应服务进程。每组只有 5 个计数样本、4 个一秒间隔，属于探索性带宽样本：

| 链路 | 平均服务进程发送速率（十进制 MB/s） | 判读 |
| --- | ---: | --- |
| 原 RDP | 4.846 | 原始位图路径带宽大 |
| 明确协商 NSCodec 的 RDP | 1.037 | 短样本下降约 79%，不代表延迟降低 79% |
| 苹果屏幕共享 | 0.159 | 观察值；客户端前后台可见性未锁定，不能据此作公平性能比较 |

重要限制：三组并非同一账号、同一时段；窗口摆放和客户端可见性未严格冻结。特别是 VNC 客户端在后台时可能减少更新请求，低发送量可能同时意味着低交付率。以上只能用于发现原始位图退化和设计下一轮实验，不能声称 VNC 比 RDP 快若干倍，也不能将压缩前后的比值当作隔离变量后的因果测量。正式基准须锁定前台可见性并同步记录客户端有效显示帧与输入延迟。

RDP 新日志实际记录 `codec=nscodec`。仅打开 Cargo feature 的第一次尝试仍记录 `codec=raw`：库的默认能力列表没有 NSCodec，必须同时广告能力与编译编码器。这是配置与构建缺少联合验证的问题。

NSCodec 动画期间，服务端五秒窗口交付约 55–56 次 display update，即约 11 次/秒；这是服务端交付速率，**不是客户端最终显示 FPS**。目标采集 30 FPS 没有变成端到端 30 FPS。原服务进程 5 秒栈采样以等待网络/事件为主，不能据此认定 CPU 编码是主瓶颈。

用户确认黑块由缩放客户端窗口触发。补充 RefreshRectangle / SuppressOutput 恢复时缓存失效后，用户仍报告黑块。因此“缺少刷新处理”只是已经发现的缺口，不能标为最终根因。必须同时观察客户端缩放是否发出刷新 PDU、服务端 surface/bitmap 的实际边界和像素、完整帧是否到达并显示。

原连接约 348 秒后结束，Windows App 主进程和来宾服务仍在，重连后文档保留。旧日志只记录正常返回，无法区分客户端请求结束、桥 EOF 与显示流结束。本轮补了桥读取失败原因；历史断线根因仍未确定。

原始短样本位于私有 `build/compare/nettop-*.csv`，分析结果为 `build/compare/bandwidth-report.json`。分析器不采集桌面或口令：

```sh
python3 tools/perf_report.py --interval 1 \
  raw=build/compare/nettop-rdp-raw.csv \
  nscodec=build/compare/nettop-rdp-nscodec.csv \
  vnc=build/compare/nettop-vnc.csv
```

## 三、按整条链路改造

| 层 | 当前缺口 | 统一设计与验收 |
| --- | --- | --- |
| 身份与控制权 | 测试口令、预登录账号；真实跨平台接管未完整验收 | 保留 UID + 审计会话 + boot ID + epoch + lease 的绑定；控制权交接原子化；旧连接不能再输入；注销后旧代次失效 |
| 采集 | 目标 FPS 与实际交付混淆；显示几何与采集缓冲生命周期缺少统一诊断 | 每帧记录 source sequence、单调时钟、尺寸、行跨度、会话/几何代次；独立统计完整帧、空闲回调和丢弃帧 |
| 本地转发 | 9.216 MB 原始全帧经 GUI socket、UID relay 到 broker；30 FPS 单跳约 276 MB/s 数据，尚未计算额外拷贝 | 分离控制与画面通道；事件驱动读写，限制待处理帧数与字节数；完整帧可以合并，依赖补丁只能重建后合并；评估在用户代理编码或受控共享内存，保持权限边界 |
| 调度 | `M2Bridge::poll` 每 10 ms 只进行一次 send，整帧需多次 socket 可写轮转；该结构可能限速，尚未分段实测确认 | 改为可写事件驱动，记录 enqueue、首次/末次 send 与排队年龄；做传输基准后再修改采集频率；不能以增加 socket 缓冲当作完整流控 |
| 编码与客户端能力 | 构建有实现、能力未广告；没有统一选择策略与可见降级信息 | 单/多用户入口共享能力策略；分别记录广告、确认、选择结果；保留兼容回退。RDP 若继续，先独立验证 EGFX + VideoToolbox，再接入多用户 |
| 画面恢复 | 差异缓存依赖客户端仍持有旧画面；本地缩放、远端改分辨率、重连未区分 | 统一 DisplayState：几何代次、完整画面基线、失效区域、恢复原因；缩放/恢复请求应触发可观测的完整恢复；视频重建 surface 并发关键帧；补丁缺基线时禁止显示 |
| 输入 | 必须与几何、控制权和会话同步 | 坐标转换绑定已确认的几何代次；缩放中拒绝旧坐标；断线释放按键/按钮；覆盖双击、组合键、中文候选与焦点切换 |
| 生命周期 | 断线原因日志不足；限时 GUI 进程，无生产级自动恢复 | 连接结束分类为用户断开、网络 EOF/超时、权限撤销、代理结束、会话代次变化、协议错误、接管；恢复不能切到控制台或其他用户 |
| 打包与权限 | 临时签名多次改变导致授权判断混乱 | 固定应用身份、版本与签名；启动检查运行进程实际权限；配置在 bundle 外。签名/发布属于单独交付项，不通过 TCC 数据库修改绕过 |
| 容量 | 双用户功能测试不能推断 32 人 | 先双用户真实客户端、再 2/4/8/16/32 人负载；记录进程数、内存压力、交换、CPU、每用户速率和延迟；VM03 固定 8 GB |

上述调度、拷贝与缓存分析属于基于源码和样本的推断，尚非完成的端到端根因证明。

为避免再次凭直觉归因，补充了 `tools/ipc_bench.py`：只在宿主本机用一个 Unix socket、同样的 1 MiB 发送缓冲请求传输 30 个 1920×1200 BGRA 合成帧。10 ms 定时调度模型约 44.8 个传输帧/秒，可写事件模型约 1565 个传输帧/秒，均完整接收 276,480,000 字节。原始记录为私有 `build/compare/ipc-model.json`。它排除了“10 ms 调度在所有条件下天然只能达到 11 FPS”的解释，支持减少轮询开销，但**没有证明这是 VM03 的主瓶颈**；还必须在来宾内逐段测量 GUI 调度、两跳 relay、编码和客户端解码。以上模型不包含采集和渲染，数字不能作为桌面 FPS 发布。

## 四、实施边界与交付顺序

1. **基础测量先行**：冻结实验配置、统一编码能力策略、记录实际 codec 与 display update 速率、桥退出原因，保存对照样本和分析器。基础改动已落地；不因此宣称显示层完成。
2. **VNC 可用主线**：Mac 原生屏幕共享和 Windows 候选客户端逐项验证账号认证、独立桌面与后台输入，再做同用户接管、跨平台恢复。若 Apple 服务不支持第三方所需语义，先明确限制，再选择独立 VNC 后端；不以共享控制台替代多用户。
3. **显示层一次整合**：建立统一几何/恢复状态与事件驱动转发，搭配故障注入和完整画面检查。黑块必须先在可重复负载下失败，再在相同负载下通过；恢复机制不能依赖用户每次重连。
4. **可选 RDP 路线**：只有 legacy 路径和 VNC 基线可测，才集成硬件编码和客户端反馈流控。维护性与多用户隔离优先，不能整体替换为单会话 macrdp，也不继续盲目叠加本地 vendor 补丁。
5. **交付门槛**：独立账号、缩放、失焦、后台、重连、权限变化、慢网络一起通过后再宣称首版可用。生产部署、冷启动 GUI 创建、系统认证和容量仍单独验收。

## 五、不可跳过的回归矩阵

- Mac/Mac、Windows/Windows、Mac/Windows；两个独立账号各运行 30 分钟，含 100 轮可核对输入和拖动。
- 客户端缩放 50%/100%/200%、至少 50 次连续调整窗口、最小化/恢复、全屏切换；远端分辨率改变单独测试。对静止背景的完整性和变化区域都做像素检查，不能只看中心动画在刷新。
- 静态桌面最后一次键入、持续滚动、照片/视频、中文组合输入、修饰键、双击与拖动；分别记录 source FPS、交付速率、客户端可见 FPS 和输入到画面更新延迟。
- 网络 RTT 0/50/150 ms、带宽约束、慢解码/慢读取、突然 EOF、代理停止、权限撤销与注销。确认队列有界、旧画面不会长时间补播，B 不受 A 影响。
- 同用户新连接接管：旧端断开、应用不退出、原文档保留、旧端复网仍不能输入；错误口令不得踢掉已登录用户。
- 1080p 首轮目标：滚动至少 15 个有效显示帧/秒、输入到画面更新 p95 < 200 ms、30 分钟零意外断连、零跨用户画面或输入；通过双用户后再扩容。

## 六、本轮已落地与未完成

已落地：统一单/多用户 NSCodec 能力广告，运行时 codec 日志，可选 display 交付率记录，桥失败原因日志，重绘请求使编码器缓存失效，带宽对照分析工具及其回归测试。应用单元测试与重绘缓存单测不能代替真实缩放测试。

本轮验证：16 个应用 Rust 单元测试、14 个库单元测试、31 个 Python 测试通过，应用 Clippy 通过。宿主 IPC 模型完整传输检查通过。共享能力策略的整理发生在来宾 NSCodec 实测之后，来宾仍运行该实测构建，未通过额外重启打断用户桌面；最终统一构建仍需下一次受控集成验收。

**未完成**：缩放黑块最终定位与修复、事件驱动转发替换、真正客户端 FPS/延迟测量、Windows VNC、多平台接管和完整稳定性矩阵。不得把本报告或上述局部改动表述为“全面完善已完成”。
