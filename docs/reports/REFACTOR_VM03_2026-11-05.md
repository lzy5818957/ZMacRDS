# VM03 链路改造与回归（2026-11-05）

环境：VM03，4 核、8 GiB、macOS 27.2 / 26B123、1920×1200；三个独立 GUI 账号保留为 virtualbuddy / UID504、rdp / UID505、vnc / UID506。系统 SessionInfo 核对：仅 UID504 的 OnConsole 为 true，UID505/506 都为 false 且 LoginDone 为 true；没有让 RDP 操作切换 VirtualBuddy 控制台。客户端是同一宿主 Mac，Windows App 11.4.4 (3132)、Apple Screen Sharing，以及官方 TigerVNC 1.16.2 macOS 构建。没有 Windows 测试机，Windows 全部标为未测。

## 已落地

- GUI 桥改为 socket 读写事件驱动，控制消息及时读取，写就绪才发送，待发送图像保持有界。保存最新完整 CVPixelBuffer，在静止桌面新连接时提供基线；SCK idle 不等于采集失败。250 ms 看门狗负责身份与租约检查。
- 差异图先重建成完整图像，再合并为单个最新快照，避免跳过依赖补丁造成客户端缺块。失去源/租约时终止，不能继续重放缓存桌面。
- RDP 首帧、周期完整重绘和 RefreshRectangle / SuppressOutput 恢复共同使差异缓存失效。支持的客户端收到整帧 Begin / End，包围同一完整快照的所有分块。库回归验证四条 strip 位于同一对帧标记内；不支持帧标记的客户端不发送它。
- 单/多用户入口统一广告 NSCodec；记录实际协商 codec、帧标记能力及可选交付计数。它们不是最终 GUI FPS。
- VNC 网关在 VM03 普通账号下运行，原生系统账号认证，上游公钥在凭据发送前核对；同账号新有效连接撤销旧控制端，其他账号独立。所有跨机通信仍在已验证的 SSH 隧道中，网关仅监听回环。
- 使用稳定 Apple Development 签名与 `/Applications/ZMacRDS Desktop.app`，通过系统设置正式添加录屏应用并核对实际 heartbeat；录屏和辅助功能均为 true。没有直接读写 TCC 数据库。
- 提供显式客户端配置 `config/ZMacRDS-fixed.rdp`、网关样例、完整 Python 运行时测试包，以及可重复的观察、接管和输入回显工具。

## RDP 黑块：失败重现与受支持模式

事件驱动、全帧恢复和帧标记部署后，Windows App 开启 **Update the session resolution on resize** 时仍能在切到半屏/全屏尺寸时复现大片黑色，只剩变化区域，随后完整重绘恢复。因此不能把新增 FrameMarker 或 RefreshRectangle 处理单独写成最终修复。

当前服务没有实现 Display Control 动态远端分辨率协商。关闭该客户端选项、固定远端 1920×1200、开启 **Fit session to window** 后，保持远端几何，仅让客户端缩放。同一负载下先做 12 次，再做 24 次，最终固定能力构建又做 12 次 Fill / Left / Right 切换，合计 48 次，均未再出现大片黑块。中间 24 次截图采样的深黑像素最大占比 1.269%，最后 12 次最大 1.208%，包含合成标记和文字；失败模式是几乎整屏黑色。这个指标只用于本次固定合成桌面的严重缺块判别，不能替代任意画面的像素相等验证。

结论：**固定远端几何 + 客户端窗口缩放的已测模式通过这组回归；动态远端分辨率仍不支持，开启时的问题没有消失。** 不宣称所有缩放路径已修复。一次窗口边缘拖动尝试没有改变实际窗口大小，不计入有效回归次数。最终服务显式关闭 DesktopResizeFlag；对照测试确认即使关闭能力位，Windows App 强制动态分辨率时仍会黑屏，所以不能将能力位修正本身写成动态分辨率修复。

## 流畅度与输入回显

事件驱动构建在初始单客户端观察中约每秒交付 29 次 display update，之前约 11 次；同时运行 VNC 双观察、原始位图输入测试和多个合成窗口时约 18–23 次。测试负载并非严格隔离，不能据此给出纯调度改造的加速倍数，也不能写成最终显示 FPS。

实际 M2 合成传输测试在 VM03 完整传送 30 个 1920×1200 BGRA 帧，276,480,000 字节，约 259 ms。它只证明桥传输没有旧 10 ms 轮询造成的低速上限，不是 GUI 帧率。

为输入延迟在独立测试编辑器添加 UID / nonce / UTF-16 文档长度 / CRC 可见条。RDP 自动客户端在发送 30 个字符后检查真正解码的像素：p50 **145.103 ms**，p95 **179.973 ms**，最大 **180.083 ms**，全部确认，32 秒测试通过。这条测试走 raw RDP；**不能外推成 Windows App NSCodec 的端到端延迟**。

Windows App 直接键入、修饰键、恢复文本已检查。CUA 在 Unicode 模式下注入单键时出现额外空格/首次键未达等现象；改用 Scancode 后 30 次输入按顺序可见。其工具调用到截图的 p95 约 594 ms，含 80 ms 按键保持及固定自动化耗时，不当作网络延迟。直接 Unicode 中文 `中文恢复-RDP` 另由协议客户端送入并从编辑器文档核对保留，区别于服务端拼音组合输入。

## VNC 实测记录

官方 TigerVNC macOS 构建曾以实际 rdp 系统账号连接原生后端并显示 UID505 桌面；Windows 客户端未测。原生共享连接没有实现项目要求的同用户踢旧端，因此新增网关。

宿主网关首轮真实接管测试通过：新 A 关闭旧 A、错误口令不关闭旧 A、B 的像素标记持续更新。后续已把网关和 Python 运行时部署到 VM03 的 127.0.0.1:5901，宿主 SSH 转发为 5907。最终网关的真实接管测试在长测前后均通过：错误口令拒绝且旧 A 保持，新有效 A 关闭旧 A，B 持续更新。最终记录为 `build/compare/vnc-takeover-post-soak.jsonl`。

首轮宿主网关 1830 秒观察在约 1556 秒由观察器超时退出，**该轮 FAIL**。立即重新连接时两个桌面均正常。原因没有确定；观察器随后改为保留半包读取任务、超时后请求一次全帧并记录详细进度，不能抹掉首轮失败或未经证明归咎服务端。

### 最终 VNC 交互长测

最终构建在 VM03 内运行，UID505/506 由两个独立进程同时连接同一入口。每个账号使用两个不同 bundle ID 的真实编辑器进程；每 18 秒切换应用、清空主文档、输入带轮次的中文文本，再鼠标拖选。双端连续读取画面，核对文档 UID/nonce/长度的 CRC 标记及独立移动标记。完整文本与非空选区还必须在应用日志中逐轮吻合，不能只凭长度标记判断输入正确。

| 指标 | UID505 / rdp | UID506 / vnc |
|---|---:|---:|
| 持续时间 | 1830.001 秒 | 1830.000 秒 |
| 完整轮次、精确文本及选区 | 100 / 100 | 100 / 100 |
| 主应用 / 辅助应用实际鼠标按下 | 200 / 100 | 200 / 100 |
| 拖选操作 / 实际 drag 事件 | 100 / 400 | 100 / 400 |
| 不同移动标记解码速率 | 29.893 Hz | 29.892 Hz |
| 整段文本可见延迟 p95 | 384.268 ms | 303.019 ms |
| 串入另一账号的文本 / 意外断线 | 0 / 0 | 0 / 0 |

整段文本每轮长度不同，包含中文；它的延迟不是单键延迟。移动标记速率是解码观察值，不是 GUI 渲染器最终 FPS，也不等价于任意视频负载。结果：`build/compare/vnc-workload-final-{rdp,vnc}.jsonl`；主/辅助应用证据：`{rdp,vnc}-{primary,secondary}.jsonl`；逐轮复核：`vnc-workload-verified-{rdp,vnc}.json`。复核将宿主文件创建时间校准到来宾原始单调时钟，排除长测之前的 3 轮 smoke；实际计数恰为 200/100 次点击。

独立单键测试使用持续读取的 ZRLE 优先解码器，每侧 34 次 ASCII/Unicode 输入，以实际解码的文档长度标记确认：UID505 p50 **41.432 ms**、p95 **60.690 ms**、最大 **364.653 ms**；UID506 p50 **46.767 ms**、p95 **145.213 ms**、最大 **205.044 ms**。单次峰值仍有长尾，不能只报 p95 隐藏它。记录：`vnc-paced-final-{rdp,vnc}.jsonl`。这是协议客户端测量，不是 TigerVNC GUI 的显示延迟。

慢接收端故障：A 暂停读取并缩小接收缓冲，网关以 `display_delivery_timeout` 移除它；B 持续更新，最大观察间隔 **789.963 ms**。A 随后重连回自己的桌面，未影响 B。记录：`vnc-slow-final.jsonl`。随后又完成一次接管回归。

### 协议与启动修正的依据

- Apple 原生服务对第三方连接默认观察模式，网关现先发 SetMode(control)，等待 2.2 秒控制初始化，再向前端宣布就绪。来源：[macvnc 的协议记录](https://github.com/bouk/macvnc/tree/7385d6c6105b9565889d95d2cf3a5e606e70ee9d)，解决了“看得见、开始几次键盘输入被忽略”的实测问题。
- 原生增量轮询出现数百毫秒长尾；网关在首次全视口请求后启用 Apple AutoFrameBufferUpdate、间隔 0，原生端按变化推送。协议布局对照 [zDesk 源码](https://github.com/andrewtheguy/zdesk/blob/179d0747121b667bbf2df790739ea3a3e5a6354d/src/vnc_apple.rs) 和其 [协议说明](https://github.com/andrewtheguy/zdesk/blob/179d0747121b667bbf2df790739ea3a3e5a6354d/docs/apple-vnc-889.md)。这些社区实现提供线索，结论以上述 VM03 输入、长测和故障实测为依据。
- 网关解析 RFB 消息边界，压缩像素不解码重编码；一个完整 framebuffer update 的发送限时 1 秒、最多 64 MiB / 4096 个矩形。慢端关闭，不能丢依赖补丁后继续。部分视口请求恢复轮询；会话/几何改变关闭连接，避免跨会话继续转发。
- GUI 代理直接从 root SSH 执行内部二进制时，重启后录屏预检为 false；同一路径、同一稳定签名经 LaunchServices `open -n … --args …` 启动后两项权限均 true、真实采集成功，重复启动 signed07/08/09 已验证。交付 `tools/start-desktop` 固定此启动方式。

实际 GUI：TigerVNC 1.16.2 通过网关以 UID506 显示独立桌面并接收键盘；Windows App 同时连接 UID505；VirtualBuddy 保持 UID504 的控制台。Apple Screen Sharing 曾直接连接原生服务通过独立桌面验证，但其 3.3 握手没有通过当前网关认证兼容性；不能把原生直连结果算成网关通过。最终只保留一个 VNC 桌面窗口。

## 07:02 后的锁定恢复复现（同日补充，尚未通过）

用户再次要求展示三个独立账号时，上轮限时 GUI 代理与 VNC 网关已经退出。重新启动后 VNC 网关认证 UID506 成功；RDP 认证 UID505 成功，但约 4.5–5.1 秒结束，Windows App 报 0x204。新 GUI 代理两项权限仍为 true，只有首个完整帧，随后 frame_age_ms 持续增长。用户会话 LoginDone 仍为 true，前台 PID 是该用户的 loginwindow；Apple 原生屏幕共享明确显示 Locked、只见壁纸。VirtualBuddy 控制台也处于锁屏。

桥接端在 capture signal 超过 3 秒时拒绝键鼠并关闭 peer，RDP 端记录 bridge_reader_ended / unexpected end of file。现有证据指向锁定会话无新采集信号时的输入保护与恢复路径，不能归因为口令错误或网络不通。控制台密码已在来宾本地验证正确，但自动桌面工具未可靠完成解锁，已请求用户手动解锁一次后继续验证。

本条复现尚未通过，前文的活跃桌面长测不包含数小时后的锁定恢复，不能以既有 PASS 覆盖这项失败。日志保留在来宾 rdp-demo10.jsonl、rdp-demo10.stderr 和 GUI 代理 demo10/events.jsonl。

后续已实施暂停与恢复状态修复，并完成真实 Windows App 锁屏、暂停输入丢弃与同一连接恢复验证，详见 [RDP 0x204 修复记录](RDP_CAPTURE_RECOVERY_2026-11-05.md)。保留上述原始失败，不以新结果覆盖其发生事实。
