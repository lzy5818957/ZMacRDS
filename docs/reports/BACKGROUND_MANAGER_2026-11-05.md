# VM03：后台代理与原生管理窗口（11月5–6日）

本轮把常驻实验桌面改为菜单栏后台代理，并增加本机原生管理窗口。VM03 为 Apple Silicon、macOS 27.2 / 26B123、4 核、8 GiB；宿主使用 macOS Windows App 和苹果屏幕共享。没有 Windows 操作系统客户端，本轮不包含 Windows 实机、32 人容量、多显示器或无人登录时自动建立 Aqua 桌面的验收。

## 交付行为

- 常驻代理无彩色 M1 大窗口、无 Dock 图标；只保留菜单栏入口。透明 8×8 本进程窗口用于确定用户显示器，采集时排除该窗口；身份失败不回落到控制台。
- 启动通过 `open -g -W` 保留用户原来的应用焦点；菜单展开时，身份、状态和本机控制处理继续更新。
- 原生管理窗口显示已配置账号、桌面代理、录屏与键鼠权限、RDP 连接及采集状态。支持 RDP 断开、桌面代理启动／停止／重启、系统 RDP 服务启动／停止／重启。不会注销用户或关闭其应用；VNC 连接不由该窗口管理。
- root 本机控制服务只接受固定动作和账号，从内核核对调用者。用户只能直接查看／操作自己；系统或其他账号操作需要独立的系统管理员验证，五分钟到期，可主动锁定或在关窗时撤销。程序不保存管理员密码。
- 指令绑定代理和系统代次，只读一次，十五秒失效；root 所有、目标用户独享读 ACL，其他用户不能读取。IPC 有长度、整条读取时间和并发上限。

安装与使用见[管理窗口](../MANAGEMENT.md)及[常驻服务](../SERVICE.md)。不限时、按 UID 的音频与常驻隧道沿用此前实现；本轮没有重新做一小时长测。

## RDP 显示与恢复：修正与验收范围

真实 Windows App 曾出现整片缺失、缩放后白块，以及静止桌面被替换为采集暂停提示。单独的位图检查客户端通过，不能证明 Windows App 的实际编码路径通过。已分别用同账号原生 VNC、RDP 行颜色摘要及客户端真实窗口对照。

确认并修复的独立问题：

- `ironrdp-nscodec` 0.2.0 原先对所有平面发送 RLE。成对字节可能使结果变大或等长，解码端却按长度区分原始与压缩内容。旧编码器对回归样本先 FAIL；现在只在严格缩小时压缩，否则发原始平面，另用零长度 alpha 表示全不透明。独立解码测试覆盖噪声、混合、常量、多行、末尾字节和上下顺序。对照 [FreeRDP 编码器](https://pub.freerdp.com/api/nsc__encode_8c_source.html)和[解码器](https://pub.freerdp.com/api/nsc_8c_source.html)，保留[来源及许可证](../../vendor/ironrdp-nscodec/ZMACRDS_PATCH.md)。
- 发送上限原先使用服务自己的8 MiB能力，忽略 Windows App 声明的1 MiB接收重组上限。现在取双方较小值，并预留帧头；测试覆盖分条编码的全部行。
- RefreshRectangle／恢复输出会主动唤醒显示链路，请求本账号的有效完整画面。暂停或已关闭来源不能重放缓存。
- 传输停顿后主动发出绑定现有连接的恢复请求；要求匹配确认和完整帧才能恢复输入。旧消息、旧代次按键及未确认的像素不能解禁输入。回归也验证关闭控制器后不会被恢复通道的强引用留住。
- 有效 Idle 样本支持静止源恢复；Blank／Suspended／Stopped 清除恢复基线。缓存复制到应用自有缓冲，避免长期保留系统表面队列。

这些修正不能合并宣称“黑块已彻底修复”。NSCodec 与全原始数据对照都曾复现缩放异常，所以 NSCodec 目前只在 `ZMACRDS_EXPERIMENTAL_NSCODEC=1` 时开放；默认兼容策略在 Windows App 未选择 RemoteFX 时使用原始 SurfaceBits，带宽成本较高。

初次缩放取样有约2.7–2.9秒恢复的失败轮次；随后被动连接虽持续40秒，UID505最终仍显示暂停提示，也记为显示失败。最终加入恢复确认后，四秒进程停顿测试的两路40秒连接保持、实际行摘要回到真实桌面，但不能把一次恢复当作长时稳定通过。后续六组放大／缩回共12个同步截图中仍有一次暂停提示，下一张恢复，持续显示验收尚未通过。

进一步记录证实 UID505 的 ScreenCaptureKit 回调曾间断约5.4秒，而主线程计时器仍正常，未发现过期 Complete／Idle 时间戳或显式源暂停状态；不能归因为时间戳或缓冲耗尽。相同配置更新的对照无效，已移除。随后改为在约一秒没有正常回调时，经原来精确绑定本账号显示器的过滤器请求一次真实单帧采集，最多每两秒一次；返回画面丢弃，不能作为采集或输入恢复授权，只有后续正常流的有效样本可以恢复。使用的是 Apple 的 [SCScreenshotManager 单帧接口](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager)，不制造测试计数器或桌面动画。新构建两账号各65秒静止连接保持，来源241次状态采样均未暂停，最终六条像素行回到各自真实桌面。来源不明的假设和失败轮次均不计入通过统计。

远端分辨率仍固定1920×1200；客户端窗口缩放不代表动态远端分辨率支持。这里的截图耗时不作为客户端输入延迟或帧率数据。

## 发现并修复的问题与失败记录

- 最初复制的旧 Editor 没有当前像素回执条，两条检查因无刷新超时，未发输入，记 FAIL。更新为当前构建的 Editor 后，重新完成全部输入与文档核对；不把失败轮次计入通过统计。
- 管理员权限初版使用系统规则别名，默认缓存期限使验证传递失效；改为本项目独立的五分钟规则，实测授权、跨进程使用及主动撤销。首次 C 字符串误当 CF 对象导致的崩溃也已修正并重新编译运行。
- 真正的 GUI 操作发现：停止代理后，直接从 root 辅助目录重新装载 LaunchAgent 被 macOS 拒绝。现在先进入目标 GUI 会话、降为该 UID，再读取该用户的已安装 LaunchAgent；不会以 root 执行可由用户修改的任务。修复后由管理窗口实际启动并重启成功。
- macOS 默认计时器在菜单展开期间暂停，会误报状态过期；改用 common run-loop modes，并实际保持菜单展开验证两侧状态仍新鲜。
- 系统自带 Python3.9 不满足 VNC 组件需要的 Python3.11+，整套测试出现3项错误及1项跳过；换用包内 Python3.13 后50项全部通过。
- 对整个 workspace（含 vendor 测试代码）使用 `clippy --all-targets -D warnings` 会被既有 vendor 测试风格规则拒绝（32项）。本项目两个 crate 的严格 clippy 全目标检查通过，vendor 的18项库测试另行通过；没有为了消除这类测试风格报告改动上游组件。

主动断开测试中的 `not enough bytes` 是预期的客户端 EOF，不作为正向 PASS；只有恢复后的完整时长及未受影响用户的完整时长计入通过。

## 使用范围

此次是 VM03 的短回归和本机管理能力验收。服务继续依赖已经登录并正常授权的用户桌面、有效证书和受限 SSH 隧道；不会跨 macOS 真正休眠或锁屏提供密码解锁。不同 Windows 客户端、完整长时稳定性、无头／多显示器、冷启动自动创建会话及容量测试仍须分别完成。
