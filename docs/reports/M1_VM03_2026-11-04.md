# M1 · VM03 采集恢复与双向输入实测

2026-11-04，实验 `vm03-m1-window-01` 通过 **PASS CAPTURE (window)**。两个普通用户在前台和后台都能持续采集自己的测试窗口；未发现串入另一账号的窗口像素。后续 `vm03-m1-recovery-09` 也通过 **PASS CAPTURE (desktop)**。**这不是完整 M1 通过**：测试窗口中的双向并发键鼠投递已通过，跨应用和会话恢复尚未验收。

## 方法与环境

- VirtualBuddy VM03，macOS 27.2 / 26B123，Apple Silicon，4 vCPU、8 GiB；沿用 M0 的账号 A（UID 502、审计会话 100202）及 B（UID 503、审计会话 100327）。
- 新增原生测试应用 `ZMacRDS-M1.app`，管理员仅在已有的 GUI 域中调度启动；账号均通过 VirtualBuddy 实际解锁并显示窗口。应用以该普通用户身份运行。
- ScreenCaptureKit 使用本进程内容枚举及独立窗口过滤器，输出 640 × 480 BGRA 帧。目标上限 2 fps，测试画面每秒更新一次；本实验不测流畅度或目标容量。
- 每帧从像素中解码 UID、随机 nonce、计数器及 CRC16，不用应用自身绘制计数代替采集结果。不保存桌面截图或视频，不采集音频。
- 启动 A，切到 B 并启动 B，保持 B 前台后再切回 A。两侧均完成正常停止并生成最终 `stop` 记录。
- 两个账号的录屏预检和辅助功能预检均未授权。本系统的本进程窗口采集接口允许这一步；不能据此推断整桌面也无需授权。

## 整桌面初版的失败证据

用户已明确允许在 VM03 的 A、B 中为测试应用开启录屏和辅助功能权限。首次尝试在未授权时返回 -3801；重编译后另遇旧签名要求不匹配。系统日志明确记录 `Failed to match existing code requirement`。通过系统设置移除旧条目、添加当前应用并完成管理员验证后，两个账号的预检均为已授权。没有直接修改 TCC 数据库或绕过授权。

正式实验 `vm03-m1-desktop-04` 中，两侧前台桌面均能返回 1920 × 1200 的本账号图像。A 切到后台时，旧流返回 `SCStreamErrorNoCaptureSource`（-3815，`Failed to find any displays or windows to capture`）并停止。B 完成登录后，A 仍持续记录 188 次后台心跳，跨度 187.002 秒；最后一条心跳的绘制计数为 327，捕获计数停在 66，距最后新帧 260.642 秒。全程 A、B 录屏与辅助功能预检均已授权，GUI 身份不变。B 的 190 次心跳期间有 193 帧成功解码。该实验明确失败，未执行输入批次；反向切换未完成。

## 恢复路径

后续只读诊断发现：在 B 前台时，A 的主显示器编号为 24，B 为 1，两者均报告 1920 × 1200、在线且活动。不能只凭旧流中断推断系统无法提供后台桌面。

已实现特定错误的有限恢复：原用户 GUI 进程等待一秒，重新枚举自身窗口及显示器，再创建新采集流，最多三次。随后 `vm03-m1-recovery-06` 的后台 A 能直接绑定显示器 24，前台 B 绑定 1，两侧都返回了本账号的新图像。该轮仅作诊断，正式切换验收使用下面的 09。

## 输入实测与判定修正

已通过正常系统设置为恢复版本启用辅助功能；A、B 均记录 `accessibility_trusted=1`、录屏预检为真。使用相同的恢复版本二进制，前台 A / 后台 B 执行 `vm03-m1-input-a-11`。每侧 100 次试验、500 个事件全部恰好一次送达本账号，无异账号标签；没有指定目标 PID，投递接口为 `kCGSessionEventTap`。两侧输入重叠约 18.784 秒，输入期间控制台始终为 502。

初版验证器报告 `received wrong keyboard text`。原始记录显示两侧各 100 个 key-down 文字均正确，全部 key-up 显示 `a`：此 Unicode 探针的虚拟键码固定为 0，AppKit 在 key-up 采用该键码的映射。Apple 明确说明框架可以忽略 Unicode 覆盖值，按键码和事件状态转换字符，见 [CGEvent Unicode API](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring(stringlength:unicodestring:))。据此，验证器仅在 key-down 核对文字；key-up 仍必须满足恰好一次、正确标签/账号/事件类型和时延。合成测试改为包含真实观察到的 key-up 字符行为，错误 key-down 文字仍被拒绝。

相同原始日志经修正后的验证器通过 `PASS CAPTURE (desktop)` 与 `PASS INPUT BATCH: console_uid=502`。结果目录同时保留修正前的失败输出、修正后输出和验证器快照；没有改写原始日志。A、B 本机事件投递最大时延分别为 19 / 15 ms，p95 为 16 / 13 ms；这不是网络 RDP 延迟。

## 仍待验收
